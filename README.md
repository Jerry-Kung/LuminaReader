# LuminaReader

> **LuminaReader** 是一个面向深度阅读场景的 AI 阅读助手项目。
> 它以 PDF 阅读为起点，尝试把传统阅读器、AI Agent、个人笔记与知识整理能力结合起来，让用户在阅读复杂书籍和长文档时获得更自然、更持续、更有帮助的 AI 支持。

---

## 1. 项目背景

很多人已经习惯使用 PDF 阅读器阅读教材、专著、论文、报告和各种电子书。但传统 PDF 阅读器主要解决的是“打开、翻页、搜索、标注”这些基础问题。当阅读内容变得复杂时，用户仍然经常遇到一些困难：

* 外文内容需要高质量翻译；
* 专业术语需要结合上下文理解；
* 某些段落、公式、图表或论证过程不容易看懂；
* 阅读时产生的疑问与笔记分散在不同页面，很难长期整理；
* 读完一本书之后，用户很难回到自己的问题、理解路径和思考记录中继续深入。

与此同时，AI 模型已经具备了很强的语言理解、翻译、解释、总结与对话能力。但现有的很多 AI 阅读工具仍然更像是“上传文档后聊天”或“对 PDF 做总结”，它们往往没有真正围绕用户的逐页阅读过程、局部困惑、笔记沉淀和长期理解路径来设计。

**LuminaReader** 想探索的是另一种方式：

> 让 AI 成为阅读过程中的助手，而不是替代阅读本身。
> 让 PDF 不只是一个文件，而是一个可以被持续理解、批注、追问和整理的阅读项目。

---

## 2. 项目愿景

LuminaReader 的长期目标，是成为一个面向个人深度阅读的 AI Reading Workspace。

它不是单纯的 PDF 阅读器，也不是一个简单的聊天机器人，而是一个围绕“阅读”这一行为组织起来的工作台。用户可以在阅读过程中随时选取内容、截图、提问、翻译、写笔记、总结思考，并让 AI 基于当前阅读现场提供帮助。

我们希望它逐步具备以下特征：

* **阅读器是入口**：用户可以像使用普通 PDF 阅读器一样打开和阅读书籍、论文或长文档。
* **AI 是阅读助手**：AI 可以帮助翻译、解释、分析、总结和追问，而不是只进行泛泛聊天。
* **笔记是核心资产**：用户自己的批注、问题、想法和理解过程应被保存、整理和复用。
* **每本书都是一个 Project**：围绕一本书逐步积累阅读记录、截图片段、AI 对话、笔记、术语和总结。
* **模型与能力可配置**：用户可以根据自己的需求选择云端模型、本地模型或不同的 AI 服务。
* **项目最终应当可开源、可迁移、可扩展**：它不应被设计成只能服务单一用户、单一模型或单一平台的封闭工具。

简单来说，LuminaReader 希望做的是：

> 一个本地优先、模型可配置、以书籍 Project 为组织单位的 AI 阅读助手。

---

## 3. 计划实现的大致功能

LuminaReader 的功能会随着项目推进逐步演进。初期不追求大而全，而是优先打磨最真实、最高频的阅读辅助场景。

### 3.1 PDF 阅读与内容选择

用户可以在应用中打开 PDF 文件，进行基础阅读操作，并通过截图、框选或文本选择的方式指定自己正在关注的内容片段。

在早期版本中，系统会优先支持 PC 端 PDF 阅读场景。

### 3.2 AI 翻译与语言辅助

用户可以选中或截图一段外文内容，请 AI 翻译为简体中文。

翻译不应只是逐句直译，而应尽量结合上下文、专业表达和阅读目的，提供更适合理解的译文。必要时，AI 也可以补充重点词汇、长句结构和术语说明。

### 3.3 AI 解释与问答

当用户遇到不容易理解的内容时，可以直接向 AI 提问。

AI 可以围绕用户选定的片段进行解释，例如：

* 这段话主要在说什么？
* 这里的关键概念是什么？
* 这一步推理为什么成立？
* 这段内容和前后文可能有什么关系？
* 能否用更容易理解的方式重新解释？

早期版本会优先处理局部内容理解问题，后续再逐渐增强对整本书上下文的利用能力。

### 3.4 笔记与批注

用户可以在阅读时记录自己的想法、疑问、摘要或评论。

这些笔记不应只是孤立文本，而应与对应的书籍、页面、截图区域或选中内容建立关联。未来，用户可以回到某一页查看当时的想法，也可以让 AI 帮助整理一段时间内积累的笔记。

### 3.5 书籍 Project

每一本导入的书籍或长文档，都可以被视为一个独立 Project。

Project 中可以逐步保存：

* 原始 PDF；
* 阅读进度；
* 用户截图或选区；
* AI 解析结果；
* 翻译与问答记录；
* 用户笔记；
* 后续整理出的术语、问题、总结和结构化资料。

这个设计可以让 LuminaReader 从一个简单工具逐渐成长为一个长期阅读系统。

### 3.6 后续可能扩展的能力

在基础阅读闭环稳定之后，项目可以继续探索：

* 章节级总结；
* 术语表；
* 开放问题列表；
* 读书报告生成；
* 基于整本书的检索与问答；
* 多书之间的关联；
* 知识图谱；
* Markdown / Obsidian / Anki 等格式导出；
* 本地模型支持；
* 插件化 AI Skill；
* 更丰富的文档格式支持。

这些能力不需要在第一版全部完成，但应当作为长期演进方向保留想象空间。

## 4. 产品形态设想

LuminaReader 初期可以采用较轻量的个人项目形态开发。

推荐的初始形态是：

> **本地运行的 PC 端 Web 应用，优先支持 PDF 阅读与 AI 辅助阅读。**

用户通过浏览器访问本地应用，打开 PDF 文件，并在阅读过程中使用右侧或侧边栏中的 AI 助手完成翻译、解释、问答和笔记整理。

这种形态有几个好处：

* 开发成本较低；
* 便于快速迭代；
* 适合个人本地使用；
* 后续可以封装为桌面应用；
* 也方便未来开源部署和社区贡献。

## 5. AI Agent 设计方向

LuminaReader 希望采用 AI Agent 思路，但早期不会追求复杂的全自动 Agent 系统。

在 V1.0 阶段，AI 更适合被设计为一个由用户明确触发的阅读助手：

```text
用户正在阅读
→ 用户选中或截图某段内容
→ 用户选择任务或提出问题
→ AI 解析当前内容
→ AI 给出翻译、解释、回答或整理结果
→ 用户继续追问或保存为笔记
```

未来，随着书籍 Project 中积累的信息越来越多，AI 可以逐渐承担更多工作，例如：

* 帮助维护某本书的术语表；
* 整理用户一段时间内的笔记；
* 归纳用户尚未解决的问题；
* 生成章节摘要；
* 根据用户的阅读记录提出复习建议；
* 在整本书范围内帮助查找相关内容。

因此，LuminaReader 的 Agent 方向不是“一开始就全自动读完整本书”，而是：

> 从用户触发的局部阅读助手开始，逐步演进为围绕书籍 Project 工作的长期阅读伙伴。

## 6. PDF 内容解析思路

PDF 文件的内容结构并不总是可靠。很多 PDF 在视觉上清晰可读，但底层文本顺序、公式、图表和排版结构未必容易被程序正确解析。

因此，LuminaReader 在早期版本中可以采用更贴近人类阅读方式的方案：

```text
用户截图或框选当前关注的 PDF 区域
→ 多模态模型识别其中的文字、公式或版面信息
→ 用户必要时修正识别结果
→ 主力 AI 模型基于解析后的内容完成翻译、解释或问答
```

这种方式不要求一开始就完美解析整本 PDF，而是优先保证用户当前正在阅读的局部内容能够被 AI 理解和处理。

后续项目成熟后，可以再结合传统 PDF 解析、OCR、目录识别、页面结构分析等工具，逐步建立更完整的书籍级上下文。

## 7. 开源化策略

LuminaReader 初期首先是一个个人项目，但设计上应尽量为未来开源做好准备。

开源化的核心目标不是立刻做成一个完整平台，而是让项目具备清晰、可理解、可复用、可扩展的基础结构。

未来开源时，项目应尽量做到：

* 可以本地部署；
* 模型配置灵活；
* 不强绑定单一云服务；
* 用户数据尽量本地保存；
* 文档结构清晰；
* 新开发者容易理解项目目标；
* 社区可以贡献新的模型适配、解析方案、阅读任务和导出能力。

开源后的 LuminaReader 可以逐步形成一个围绕 AI 阅读场景的小型生态：

* 有人贡献新的阅读辅助能力；
* 有人适配新的模型服务；
* 有人优化 PDF 或 OCR 解析；
* 有人开发新的笔记导出方式；
* 有人针对不同学科或不同文档类型设计更好的 AI Prompt / Skill。

但在项目早期，最重要的仍然是：

> 先把一个真实可用、自己愿意长期使用的阅读闭环做出来。

## 8. V1.0 版本计划

V1.0 不追求完整知识库，也不追求复杂自动化。它的目标是跑通最核心的阅读辅助闭环。

### 8.1 V1.0 的核心目标

V1.0 应让用户能够完成下面这件事：

```text
打开一本 PDF
→ 阅读到某个不理解或想深入处理的片段
→ 截图或框选该片段
→ AI 识别并解析内容
→ 用户让 AI 翻译、解释或回答问题
→ 用户可以继续追问
→ 用户可以把有价值的内容保存为笔记
→ 所有内容归档到当前书籍 Project 中
```

如果这个闭环足够顺畅，V1.0 就是成功的。

### 8.2 V1.0 预计包含的功能

V1.0 计划实现：

* PDF 文件打开与基础阅读；
* 每本书创建一个独立 Project；
* 用户可以截图或框选 PDF 内容；
* 多模态模型解析截图内容；
* 用户可以查看并修正解析文本；
* AI 翻译选定内容；
* AI 对选定内容进行解释；
* 用户可以围绕选定内容提问；
* 用户可以继续多轮追问；
* 用户可以添加与页面或片段关联的笔记；
* 用户可以保存 AI 回答到笔记或历史记录；
* 每个 Project 保存基本阅读记录、截图、解析结果、问答和笔记；
* 支持基础的模型配置；
* 具备基础 README 和启动说明。

### 8.3 V1.0 暂不重点实现的功能

V1.0 暂不重点实现：

* 全书自动解析；
* 完整 RAG；
* 完整知识图谱；
* 多书关联；
* 多用户系统；
* 云端同步；
* 移动端；
* 复杂插件系统；
* 完美 OCR；
* 对所有 PDF 类型的完整兼容。

这些方向可以在后续版本中逐步探索。

## 9. 发展路线草案

### V1.0：基础阅读闭环

重点是 PDF 阅读、截图解析、翻译、解释、问答、笔记和 Project 归档。

### V1.x：阅读体验增强

在 V1.0 基础上优化：

* 更好的侧边栏体验；
* 更好的历史记录；
* 更好的笔记管理；
* 更稳定的模型配置；
* 更清晰的 Project 页面；
* 更好的错误处理与提示。

### V2.0：书籍 Project 记忆增强

开始让每本书拥有更强的结构化记忆：

* 目录识别；
* 章节总结；
* 术语表；
* 开放问题；
* 重要片段收藏；
* 笔记归类；
* Project 导出。

### V3.0：上下文与知识体系

进一步探索：

* 基于整本书的检索；
* 章节级问答；
* 多书关联；
* 知识图谱；
* 学习路径；
* 阅读报告；
* 更完整的本地模型支持；
* 插件化能力。

这个路线只是草案，不应过早限制项目演进。实际版本规划应根据真实使用体验和开发进展不断调整。

## 10. 当前阶段最重要的事情

项目刚启动时，最重要的不是设计一个庞大的系统，而是尽快验证核心假设：

> 当用户阅读 PDF 时，如果可以方便地选取当前内容，并让 AI 进行高质量翻译、解释、问答和笔记沉淀，这是否真的能显著改善深度阅读体验？

因此，当前阶段应优先关注：

* 最小阅读闭环是否顺畅；
* AI 输出是否真的有帮助；
* 用户是否愿意持续保存笔记；
* Project 形式是否适合长期阅读；
* 多模态解析是否足以支撑早期使用；
* 项目结构是否方便后续开源与扩展。

只要这些问题得到初步验证，LuminaReader 就有继续扩展的价值。

## 11. 项目一句话总结

**LuminaReader 是一个以 PDF 阅读为起点、以书籍 Project 为组织单位、以 AI Agent 为辅助能力的深度阅读助手。它的目标不是替用户读书，而是帮助用户更好地理解、追问、记录和整理自己的阅读过程。**

## 12. 本地启动（V0 阶段）

V0 阶段的启动方式、配置项与故障速查由 `claude_docs/setup-and-run.md` 维护，本节仅给出最短路径。

**前置依赖**：Node.js ≥ 20、Python 3.12、`uv` ≥ 0.4、npm、Git。

**初始化**：

```powershell
# 后端
cd backend
uv sync
Copy-Item .env.example .env   # 编辑 .env，填入 OPENAI_API_KEY / BASE_URL / MODEL
cd ..

# 前端
cd frontend
npm install
Copy-Item .env.example .env
cd ..
```

**启动**（两个独立终端）：

```powershell
.\scripts\dev-backend.ps1     # 后端，默认 http://127.0.0.1:18086
.\scripts\dev-frontend.ps1    # 前端，默认 http://localhost:5173
```

完整流程、配置项语义、端口冲突应对、常见故障速查见 [`claude_docs/setup-and-run.md`](./claude_docs/setup-and-run.md)。
